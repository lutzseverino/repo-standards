# Contextual scope specification archive

Historical snapshot of [issue #41](https://github.com/lutzseverino/repo-standards/issues/41)
as published before implementation. The GitHub issue is authoritative; this
archive records the accepted design, not currently available CLI behavior.
See [architecture](architecture.md) and the public protocol documentation for
implemented contracts and remaining lifecycle work.

## Problem Statement

A reusable standards source cannot currently identify maintained projects in unfamiliar repository layouts or authorize a complete documentation migration without knowing the adopting repository's file locations in advance. Broad documentation-directory targets conflict with exact-owned configuration beneath them. After complete adoption, the CLI also cannot deliberately re-adopt unchanged standards and CLI versions to cover projects added later.

Repo Canon exposes these needs: discover maintained projects, including those missing a project README; distinguish them from fixtures, generated output, and organizational directories; reorganize existing documentation and repair links; and preserve exact-owned shared configuration. These semantic standards belong to the author. Repository Standards needs a generic way to turn them into reviewable, concrete contextual scope.

## Solution

Add author-supplied discovery guidance that the adoption agent resolves to individual file paths before confirmation. Enumerate project READMEs, existing documentation sources, intended destinations, directory introductions, and link-repair files. Reuse the existing disjoint target model and exact-content protections instead of introducing protected-directory subtraction or an authored protection language.

The CLI verifies the proposal's structure, target safety, conflicts, evidence references, and freshness. The adopter reviews semantic coverage and confirms one complete inspection. If more files are discovered during an eligible active run, permit explicitly confirmed additions to that declaration's scope. Never remove or transfer targets within that run, or authorize earlier out-of-scope writes retrospectively.

Add explicit same-pin re-adoption for repository growth. Preserve existing v1 sources, initial clean-start requirements, product-owned adoption orchestration, immutable exact baselines, and the distinction between historical evidence and current compliance.

## User Stories

1. As a standards author, I want to describe where contextual guidance applies in semantic terms, so that one source works across unfamiliar repository layouts.
2. As a standards author, I want discovery guidance to be separate from contextual-work guidance, so that identifying targets and changing their content have clear purposes.
3. As a standards author, I want discovery to use the existing repository-guidance declaration kind, so that I do not need another content-ownership model.
4. As a standards author, I want every profile validated for source-owned facts without executing author code, so that malformed sources fail before publication.
5. As an adopter, I want maintained projects without READMEs included, so that discovery does not depend on an existing document.
6. As an adopter, I want fixtures, generated output, and organizational directories assessed against the author's criteria, so that superficial filenames do not establish project membership.
7. As an adopter, I want included and excluded candidates explained, so that I can correct semantic mistakes before authorizing work.
8. As an adopter, I want unresolved membership questions to block confirmation, so that incomplete discovery cannot be presented as complete coverage.
9. As an adopter, I want an explained empty scope to be valid, so that genuinely inapplicable guidance does not require invented targets.
10. As an adopter, I want the declaration and its operations to remain active when discovery finds no targets, so that empty scope does not silently skip checks or fixes.
11. As an adopter, I want to review concrete existing and missing file paths, exact changes, operations, and exclusions in one inspection, so that one confirmation covers the complete adoption.
12. As an adopter, I want inspection to remain read-only and free of author-code execution, so that discovery does not itself alter my project.
13. As an agent, I want to plan migration sources, destination filenames, and link repairs before editing, so that every required change has confirmed scope.
14. As an adopter, I want exact-owned content omitted from contextual scope and accidental overlaps rejected, so that documentation can move around exact configuration without changing its ownership.
15. As an adopter, I want stale proposals rejected when relevant project state or observation inputs change, so that confirmation covers the state actually used to decide scope.
16. As an agent, I want discovered scope presented through the existing concrete target representation, so that operations and assessments share one interpretation of allowed files.
17. As an adopter, I want additions, deletions, edits, and executable-state changes accounted for, so that documentation moves and omitted changes remain reviewable.
18. As an adopter, I want observed out-of-scope work and exact-content corruption to leave adoption incomplete with changes preserved, so that failure does not become silent success or automatic data loss.
19. As an agent, I want to request additional file paths during an eligible active run, so that a newly discovered destination or link repair can receive explicit confirmation.
20. As an adopter, I want earlier work checked against the scope that authorized it before any expansion, so that later confirmation cannot legitimize an earlier violation.
21. As an adopter, I want installed expectations, source, profile, pins, HEAD, and index preserved during scope expansion, so that continuation cannot redefine the adoption I authorized.
22. As an adopter, I want removing or transferring targets within an active run rejected, so that this recovery interface remains limited to additions.
23. As an adopter, I want a mistaken target that must be withdrawn to remain an explicit incomplete result, so that an unsupported correction is not disguised as accurate final governance.
24. As an agent, I want fixes replayed for expanded scope and fresh assessment and checks required, so that newly authorized targets receive the declaration's complete behavior.
25. As an adopter, I want fix effects, agent work, confirmations, and interruption evidence preserved across expansions and retries, so that recovery cannot erase earlier work from the record.
26. As an adopter, I want to re-adopt unchanged standards and CLI versions deliberately, so that newly added projects can be covered without publishing an artificial standards update.
27. As an adopter, I want scope recomputed for a new clean adoption and removed governance reported without deleting content, so that current applicability can change between runs.
28. As an adopter, I want retained guidance and historical scope evidence available in a fresh checkout, so that the previous adoption remains explainable if the source disappears.
29. As an adopter of an existing v1 source, I want its default format and execution behavior preserved, so that this capability does not silently migrate my standards.
30. As an independent standards author, I want the same product-owned discovery and adoption interfaces as Repo Canon, so that the product does not embed one author's policies or workflow.

## Implementation Decisions

1. **Keep the existing deep modules.** The Resolver remains the sole interpreter of the author format. Repository state validates project-specific scope, observes freshness, and records adoption progress. Execution consumes concrete targets and verifies observed effects. Adoption orchestration owns the agent procedure and confirmation. Source acquisition retains its public pinned-source contract. Share the existing target-validation and execution machinery rather than building an independent discovery execution engine.

2. **Add a deliberate author-format version.** Introduce `repo-standards/v2` while preserving v1 support. A repository declaration keeps `guidance` and chooses exactly one of explicit `targets` or a `discovery` reference to a regular source file. Reference and retain both guidance files. Other declaration kinds, operation declarations, and the two-level profile model remain unchanged. Unknown fields and unsupported formats fail explicitly.

3. **Resolve discovery to files only.** Each discovered target is an individual repository-relative file path, which may be absent before adoption. Discovered directory trees, globs, repository-root write scope, authored `protect` fields, subtraction of exact descendants, and partitioning contextual trees with exclusions are not part of this feature. Source-authored explicit directory targets retain their existing disjoint behavior.

4. **Keep source resolution separate from project scope.** A proposal cannot rewrite the resolved selection, declaration IDs, guidance, operations, or profile. Materialize discovered repository guidance into the existing explicit-target representation for execution. The inspection binds both the selected source declarations and their project-specific targets. Operations receive their declaration's concrete targets; they do not independently interpret discovery guidance.

5. **Preserve ownership rules.** Use the existing overlap, reserved-target, case-folded, Unicode-normalized, ancestor, symlink, and special-file checks. Omit exact content from contextual proposals and reject accidental collisions. No target may be governed by two active declarations. Profile exclusion removes its declaration and operations, not a global path entitlement or prohibition. Ignored or otherwise unrecoverable replacement content and unrelated existing skills retain their current protection. Exact bytes, executable state, and skill inventories remain immutable after installation, including against that declaration's own fixes.

6. **Separate static and project-specific validation.** Source validation checks every profile's schema, references, operations, explicit targets, and all determinable conflicts without running author code. It cannot prove unresolved discovery safe or semantically complete for an unknown project. Inspection validates concrete discovery targets and evidence for the selected profile. A valid source is not evidence of completed discovery.

7. **Use two-pass inspection.** When required scope is absent, `inspect` returns discovery instructions, an eligible evidence inventory, a discovery request identity, and a blocker preventing adoption. The agent supplies a versioned proposal through `--scope`. A valid proposal produces a complete inspection. `start` receives the same proposal and the confirmed inspection identity. Temporary proposal files stay outside the adopting project. No separate discovery command or separate mandatory scope approval is introduced.

8. **Bind structured evidence without claiming semantic proof.** Use a new `repo-standards/scope/v1` proposal with exactly one entry per active discovery declaration and no entries for explicit or excluded declarations. Entries contain concrete file paths, a coverage explanation, candidate inclusion/exclusion reasons, eligible evidence references, and unresolved questions. Evidence may identify observed files, directory inventories, or target absence; the CLI derives their identities. A missing project README also needs positive membership evidence. Empty scope requires explanation and evidence, and does not remove operations. Malformed, missing, duplicate, or invalid references cannot authorize adoption; unresolved questions produce a non-startable report. The agent interprets meaning and the adopter reviews completeness.

9. **Make confirmation deterministic and fresh.** Bind the exact selection, requested action, complete tracked and non-ignored project snapshot, target safety observations, relevant effective observation settings and consulted ignore inputs including absence, and any active run/scope revision. Normalize unordered lists while retaining rationale text in the identity. Changes before consuming a confirmation invalidate it. Ignore inputs outside tracked project content must not silently affect classification. Retain only relevant observation information, not unrelated Git configuration or credentials.

10. **Keep observation guarantees bounded and honest.** Required evidence and target observations must be complete; inaccessible material, detected instability, or exhausted limits block confirmation or completion. Do not silently omit unavailable material or treat a read failure as absence. Observe the individual confirmed targets and ancestors as well as the eligible project snapshot, so a named file cannot disappear from evidence merely through changed ignore classification. This does not add continuous monitoring, atomic filesystem snapshots, or a complete inventory of unlisted ignored siblings. Existing source-authored directory behavior and complete exact-owned inventories remain as currently contracted. Ignored untracked material cannot become a hidden discovery dependency.

11. **Preserve the adoption sequence.** Verify confirmation and prerequisites, install exact content and runtime state, run repeat-safe fixes, perform contextual work and assessment, run checks, and verify final integrity. All initial starts retain clean committed-project requirements. Expected adoption writes are not compared to an immutable pre-start project snapshot as though no work had been authorized: subsequent observations are validated at the appropriate phase and scope revision. Recheck semantic scope after fixes and during contextual assessment; a need for additional files never grants them automatically.

12. **Observe operations through the same scope.** For v2, validate each fix's observed changes against its owning declaration's concrete targets. Checks remain read-only. Observe and report violations without claiming host or network sandboxing. Preserve separate operation outcomes, agent assessments, and exact-integrity evidence. Resource retention is not a restriction on what trusted code can access.

13. **Account for moves with existing evidence.** Record deleted sources and created destinations rather than adding a rename protocol. The agent explains their correspondence and preservation of useful content. Every destination and link-repair file must already be confirmed. Missing, false, or out-of-scope changed-path evidence prevents completion.

14. **Limit active amendments to additions.** `inspect --amend-scope` produces a read-only discovery/amendment inspection from the active run. `resume --amend-scope`, with the proposal and `--confirm`, accepts it and continues execution. Per declaration, the replacement target set must contain every previously authorized target; equality permits reconfirming unchanged scope against fresh state. Do not remove targets or transfer them between declarations. Explicit source targets, declaration contents, and the selection remain fixed. If correct completion requires withdrawing a mistaken target, leave the run incomplete and report the reconciliation limitation. Free recomputation remains possible before initial confirmation and in a later clean adoption.

15. **Require an eligible continuation.** Permit amendments at contextual handoff or a later contextual/scope/check block only when author operations have definite outcomes, no author process remains active, and installed integrity passes. Preserve run HEAD and index while binding the existing adoption working changes into confirmation. Initial clean-start rules do not apply to this explicit continuation. Uncertain work requires the existing explicit retry first. Amendment confirmation cannot be combined with assessment submission or retry in one invocation; it cannot change source, profile, or pins or perform a new exact installation.

16. **Prevent retroactive authorization durably.** Before accepting additions, validate every observed interval against its outgoing scope, and persist that validation with the new scope revision and confirmation. A crash must not leave it ambiguous whether expansion was accepted. The final union of targets alone is insufficient evidence of authorization. Existing violations must be reconciled before amendment.

17. **Preserve attribution through replay and recovery.** After confirmed expansion, rerun repeat-safe fixes with the expanded targets and require fresh contextual assessment and checks. Keep separate fix and agent observation intervals and their evidence across expansions and retries. Resetting a post-fix baseline must not erase earlier agent work. A further scope expansion requires another confirmation. Retain the existing concurrency, process-outcome, installed-progress, explicit retry, and abandonment guarantees; abandonment does not turn partial installation into reusable complete ownership.

18. **Add explicit same-pin re-adoption.** `inspect --readopt` followed by confirmed `start --readopt` deliberately starts a new run of the retained current selection. The action is part of inspection identity; ordinary retained inspection stays non-startable. Re-adoption uses existing v1 targets/protocols for v1 sources and fresh discovery for v2 declarations. Preserve initial cleanliness and exact-drift blocking. Do not combine re-adoption with source, profile, or pin changes. Standards and CLI updates remain independent existing operations and use applicable fresh discovery when needed.

19. **Distinguish changes within and between runs.** During a run, discovered scope only grows per declaration. A new clean adoption may recompute scope completely. Report additions and removals relative to the prior complete adoption, preserve content when governance ends, and never infer deletion from exclusion or retirement. An active run's history remains evidence of the work actually authorized.

20. **Retain explainable evidence.** Retain discovery guidance, accepted proposals and rationale, evidence references and observation identities, concrete scope, and amendment confirmations and interval records sufficient to explain earlier authorized work. Retained inspection describes historical scope without implying current coverage. Fresh discovery for current retained standards works without the original source; obtaining a new standards revision still requires source acquisition, and obtaining the CLI retains its existing package/cache prerequisites.

21. **Version only changed protocol shapes.** Extend inspection and assessment through explicitly versioned interfaces where discovery, run revision, or scope-validity evidence changes their schemas. Keep the existing operation-result format. Reuse the existing operation-input target representation and format when its shape is unchanged; do not introduce a protection-aware operation protocol for the removed directory-subtraction feature. Older clients must reject formats they do not support. Version identities do not require duplicating the resolver or execution engine.

22. **Keep prerequisites and remote setup within their existing contract.** Executable/version prerequisites remain preflight checks. Authored operations may discover missing subprocess dependencies, authentication, or remote permission and report incomplete work; this feature does not add a prerequisite dependency graph or remote-state confirmation. Repeat-safe GitHub setup and final readback belong to the standards source. Durable final check messages can carry concise readback evidence; local logs do not establish fresh-checkout evidence or remote rollback guarantees.

23. **Update the product-owned workflows and contracts.** The adoption skill performs discovery, obtains one complete confirmation, revalidates scope, requests eligible additions, and distinguishes re-adoption from updates and retries. The authoring skill teaches the new format and honest source-validation limits. Public author, inspection, operation, assessment, and lifecycle documentation must agree with implementation. This specification explicitly changes the prior architecture's fixed author-supplied scope, affected-target-only inspection freshness, immutable run scope, and same-pin non-startability; its disjoint ownership and initial clean-start rules are preserved.

## Testing Decisions

- Use one primary testing seam: the installed public CLI against real temporary Git repositories. This is the existing agreed seam for source validation, inspection, adoption, assessment, updates, and recovery. Exercise modules through that interface rather than testing internal organization or introducing another public testing surface.
- Good tests assert observable results: exact unchanged bytes and modes, confirmed paths, stable identities, actual filesystem changes, operation outcomes, durable evidence, blocked transitions, and safe next actions. Existing installed-CLI source-validation, path-conflict, contextual-assessment, update, retained-state, and interruption tests provide prior art. Fixture acquisition may replace network acquisition at the existing seam without introducing local-directory adoption as a public capability.
- Source-format tests cover every profile, strict fields/references, explicit and discovered declarations, v1 compatibility, unresolved project scope, and source validation that never runs author code.
- Discovery tests apply the same source to two unfamiliar layouts, including a maintained project with no README and misleading fixture/generated/organizational candidates. Validate explained exclusions, positive membership evidence, empty scope with operations still active, and unresolved questions that block confirmation.
- Inspection tests prove read-only behavior, complete proposed changes and operations, missing-proposal blocking, duplicate/invalid evidence rejection, normalized identity stability, and stale confirmation after project, rationale, selection, or relevant ignore/observation input changes. Cover missing inputs and absent targets, unreadable evidence, and observation failure without a misleading partial success.
- Ownership and migration tests enumerate individual old files, new destinations, and link repairs around exact-owned configuration. Assert removal/creation evidence and useful preservation separately. Reject exact/reserved overlaps, directory or glob targets in discovered scope, unsafe ancestors, case/Unicode aliases, omitted changes, and invented additional filenames. Verify existing explicit directory scopes retain their disjoint semantics.
- Execution tests verify concrete operation targets, observed out-of-scope fixes, mutating checks, named targets becoming ignored, stale assessment, and final exact corruption. Failures preserve work and cannot redefine baselines. Do not claim detection of all unlisted ignored sibling changes or transient changes between observations.
- Amendment tests cover fresh confirmed additions in an eligible dirty run, same-scope reconfirmation, stale confirmation, attempted removal/transfer, explicit-target or selection changes, outstanding violations, integrity failures, and active/uncertain author processes. In particular, a write outside the old scope must not become valid merely because the next proposal includes that file.
- Replay and interruption tests preserve earlier agent edits even when replayed fixes touch the same files, keep fix and agent intervals separate, and require renewed assessment/checks. Interrupt before and after amendment acceptance and during fix replay; recovery must retain an unambiguous accepted revision and prevent evidence loss or duplicate authorization.
- Re-adoption tests cover unchanged v1 and v2 pins, newly added projects, ordinary retained inspection remaining non-startable, local exact drift, scope removals between runs without deletion, and fresh discovery from retained inputs when the source is unavailable. Exercise compatible standards and CLI updates as well as unchanged pins.
- Run the required repository validation and the installed behavior on macOS and Linux. Published-path verification and a separate real-agent journey must demonstrate useful discovery, documentation migration, confirmed additions, and re-adoption. A second independently authored source must use the same generic interfaces. Scripted evidence proves deterministic contracts; real-agent evidence evaluates semantic usefulness. No implementation or new runtime tests were performed during specification authoring.

## Out of Scope

- Implementation ticket planning or creation, implementation dispatch, or product implementation as part of publishing this specification.
- Repo Canon policy changes, repository provisioning, publication, or live adoption; its remaining content, manifest, automation, operation, and skill-snapshot authoring is separate work.
- Product-specific project classifiers, author-executed discovery hooks, additional profile composition, adopter-selected subsets, source/profile switching, or automatic prerequisite installation.
- Discovered directory write scopes, arbitrary future descendants, globs, root write scope, authored protection syntax, exact-descendant subtraction, or contextual ownership partitioning.
- Removing or transferring targets during an active run, silently correcting a mistaken target, retrospective authorization, automatic recovery from abandoned partial installation, automatic commits, or blanket rollback.
- A built-in GitHub governance subsystem, remote ownership/freshness baselines, immutable remote readback guarantees, or a new declarative dependency/permission preflight graph.
- Host/network sandboxing, continuous filesystem monitoring, atomic snapshot guarantees, complete observation of unlisted ignored siblings, and independent v1/v2 execution engines.

## Further Notes

This specification incorporates the final simplicity review: discovered scope is an explicit file list and active amendments are additions only. The broader protected-directory design and shrinking-scope recovery discussed earlier are superseded. The accepted costs are earlier filename planning, potentially longer reviewable proposals, and an explicit incomplete result when correcting an initial mistake requires withdrawing scope after work starts.

The core required outcomes remain covered. The design reuses existing path ownership and move evidence, while keeping the additional state necessary to make confirmation, scope expansion, and recovery honest.

The product's earlier accepted baselines are [Repository Standards v1](https://github.com/lutzseverino/repo-standards/issues/1) and [Author standards from confirmed preferences](https://github.com/lutzseverino/repo-standards/issues/25). This specification is sufficiently specified for the `ready-for-agent` label; that label does not dispatch implementation or create implementation tickets. No additional unresolved product-design blocker was identified after the accepted simplifications.
